A demo of detaching POS client↔server communication via a Mediator. Instead of the POS Client talking to the Backend for everything, a Mediator (S3-compatible object storage on UpCloud) carries the bulk of the traffic — config/catalog downloads and receipt uploads — while the Backend is only touched briefly to log in and to hand out short-lived upload URLs.

This page shows that traffic live. Nothing below is stored — it's activity observed since you opened this page.

POS Client

A Java application standing in for a real point-of-sale terminal. It consumes configuration and price catalog data, and produces receipts. In this demo it runs headless, simulating a device: logging in, polling for updates, and periodically generating and uploading synthetic receipts on its own.

Mediator

An S3-compatible object storage bucket on UpCloud. It's the detachment point of this architecture — config/catalog live here for the client to read directly, and uploaded receipts pass through an inbox before being archived. Almost all traffic in this demo flows through it rather than hitting the Backend.

Backend

A Node.js/Fastify server. It owns the tenant's configuration and catalog, issues short-lived login tokens and upload URLs, and processes receipts out of the Mediator's inbox. In this demo it's deliberately thin, touched only to bootstrap a session or hand out an upload URL.

Security

How security is handled today

  • The client never holds long-lived credentials for the Mediator — every access is a presigned URL, scoped to one object, expiring in 10 minutes.
  • The Backend-issued JWT (from /login) is the only thing authorizing calls back to the Backend itself (/upload-receipts, /monitor/events), and it also expires quickly.
  • Every client-supplied identifier (device id, receipt id) is checked against a strict allow-list pattern before it's used to build a storage path — closes off path-traversal / arbitrary-write attempts.
  • Backend secrets (S3 keys, JWT signing secret) live only as Fly.io secrets, never committed to the repo.
  • Monitor event reports are validated (known type, bounded field lengths, bounded request size) before being broadcast to viewers.

What's deliberately not done (this is a demo)

  • /login accepts any well-formed device id — there's no device enrollment or allow-list, so anything can start a session claiming to be any device.

Toward a zero-trust client

  • Real enrollment: issue each device its own credential (a client certificate or pre-shared secret) when it's provisioned; /login verifies that credential instead of trusting a self-chosen id.
  • Scope by identity: bind presigned upload URLs to the authenticated device's own path (e.g. inbox/<deviceId>/<receiptId>.json) so one device's credential can never be used to write into another device's namespace.
  • Continuous verification: short-lived tokens already help; a fuller zero-trust posture re-checks device health/identity periodically and can revoke instantly, rather than just waiting out a fixed expiry.
  • Attestation: verify the client binary/runtime hasn't been tampered with before granting it a session (code signing, remote attestation).
  • Stronger transport: mutual TLS between client and Backend instead of relying on a bearer token alone.
  • The core shape of this architecture already fits zero-trust well: the Backend is the single policy-enforcement point, and the client never talks to the Mediator without a fresh, narrowly-scoped credential issued for that one call.
